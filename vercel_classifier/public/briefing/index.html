RESEARCH FINDINGS

Understanding the work with AI

A briefing for city officials on the process, results, and next steps for assisted permit classification.

Executive summary

We tested whether AI can organize work descriptions into six recorded permit categories. This could help staff sort records and find descriptions that need review. Predictions were compared with recorded labels, errors were examined, and instructions were revised with labeled examples.

83.7%Best revised accuracy
172Permits evaluated per model
6Work categories

The strongest revised model, muse-glimmer, matched the recorded label on 144 of 172 permits. This supports exploring a staff-assistance pilot.

Evaluation mistakes informed the prompt revisions. These are diagnostic results; a fresh unseen sample is needed before claiming performance on new City records.

Analysis

Our process

  1. Prepare: de-duplicate permits and descriptions. Exclude 505 records in 28 description groups with conflicting labels.
  2. Balance: select 300 records, 50 per category. Save 120 for prompt development and 180 for evaluation with no overlapping permits or normalized descriptions.
  3. Compare: the original notebook tests six conditions: two models (llama-4-scout and gpt-oss-120b) × zero, one, and six labeled examples, with 180 evaluation permits per condition. Saved notebook outputs supply the baseline scores below.
  4. Revise: compare eight- and ten-example instructions with three models through OpenRouter. Keep eight earlier error-review permits excluded, leaving the same 172 evaluation records. The ten revised examples come from the development split.
  5. Audit: count invalid and failed responses as incorrect. Preserve predictions, prompts, examples, and error reviews.

Categories: MACHINERY, DEMOLITION DUMPSTER, CRANE, BARRICADE, MATERIALS, and SCAFFOLD.

Original experiment: six model–prompt conditions

The original category_analysis.ipynb ran 2 models × 3 example counts (0, 1, and 6) = 6 conditions, totaling 1,080 requests. Zero examples tests instructions alone; one supplies one labeled example total; six supplies one example per category. Every condition uses the same saved 180 permits, with 30 per category. This isolates the effect of examples within each model.

Scout performed best with six examples: 77.22% (139/180), compared with 75.56% with none and 73.89% with one. GPT-OSS performed best without examples: 74.44% (134/180), declining to 70.56% with one and 68.33% with six. The result shows that adding examples can help one model while reducing another's performance; prompt selection should be tested, not assumed.

Scores are transcribed from the notebook's saved output table; original raw prediction CSVs are unavailable locally. These 180-record baseline scores should not be directly compared with later 172-record revisions as a measured improvement: the prompt, provider, and evaluation sample changed.

Follow-up experiment results

Accuracy measures agreement with recorded labels. Macro-F1 balances precision and recall for each category, giving all six equal weight; 1 is perfect agreement.

The revision improved muse-glimmer from 80.81% to 83.72%, while gpt-oss-120b fell from 78.49% to 76.74% and llama-4-scout fell from 75.00% to 72.67%. Scout failures increased from 8 to 19. More examples did not improve every model.

What the errors teach us

Material storage can be confused with barricades, and crane work with general machinery. The revised prompt emphasizes the permit's main purpose instead of a single noun. Descriptions may omit equipment or context, and some recorded labels appear inconsistent. Label agreement does not independently verify on-site work.

The separate Jetstream eight-example run failed on all 172 records for every model. That unsuccessful run does not meaningfully measure classification ability.

The balanced sample does not represent citywide work-category frequencies. The study does not measure time saved, cost savings, enforcement outcomes, or fresh-sample performance.

Takeaways

  • Pilot assisted triage: suggest categories for staff review before they affect public reporting or operations.
  • Validate on new records: freeze the prompt and test an independently reviewed sample reflecting the City's real category mix. Report category errors and response failures.
  • Improve descriptions: ask for the main purpose, equipment, storage, disposal, and access needs; reconcile conflicting labels with permit staff.
  • Measure practical value: track review time, corrections, response reliability, and API cost before expanding.
  • Preserve the audit trail: retain source labels, suggestions, model and prompt versions, and staff corrections.

FULL-TAXONOMY PILOT

Filling gaps in permit work types

A 250-permit study of how AI can propose missing work types across the full observed dataset taxonomy.

Executive summary

Blank work types make it harder to organize permits and compare activity across the city. This follow-up used Muse Glimmer to propose categories for 250 randomly selected, entirely uncategorized permits. It expanded the instructions from six construction-staging categories to all 21 work types observed in the source CSV, with an additional OUT OF SCOPE option when the evidence did not support a category.

225 / 250Permits with a proposed work type
25Abstentions left blank for review
21Observed work types allowed

All 250 requests returned valid responses. Categories were proposed for 90% of the sample, while 10% remained blank. 90% is assignment coverage, not classification accuracy. These permits have no existing work-type labels against which to score predictions.

The expanded prompt has not been accuracy-evaluated. The earlier 83.72% score applies to the six-category prompt on labeled evaluation records; it does not validate this new prompt or the 250 unlabeled permits.

Analysis

Why the scope had to expand

The original six categories describe construction staging: machinery, dumpsters, cranes, barricades, materials, and scaffolds. Blank work types also occur in opening, pole, sidewalk repair, and other permit families. All 250 sampled permits were outside the original CONSTRUCTION STAGING permit type, making the narrower prompt a poor fit.

The new prompt discovers every nonblank work type in the source CSV. It retains the ten staging-boundary examples and adds 21 observed labeled examples across additional types, with up to two per additional type where suitable examples are available. Added examples exclude prior development/evaluation descriptions and conflicting-label records. Work description and permit type are supplied together; permit type supports interpretation but is not itself a work-type answer.

All 21 observed work types

All observed work types were allowed; not every allowed type was predicted in this random sample. This does not establish coverage of work types absent from the source CSV.

Sample and reproducible process

  1. Select at permit level: use only permits with blank work types on every segment, usable descriptions on every row, and one consistent description. Sample 250 unique IDs uniformly with seed 42; this is not a balanced sample by work type.
  2. Predict once per permit: use Muse Glimmer through OpenRouter, with eight concurrent workers and saved checkpoints. Keep failures and incomplete requests visible.
  3. Preserve source records: export proposed labels separately and propagate them to the sampled permit's segment rows. Existing source labels and the original CSV are unchanged.
  4. Abstain when needed: OUT OF SCOPE means unsupported activity or insufficient evidence. Abstentions keep their reason and confidence, require review, and leave proposed and populated work-type fields blank.

What the sample produced

GENERAL EXCAVATION (103), RESTORATION (55), and POLE (35) were the most frequent proposals. These broader categories account for work the original staging-only taxonomy could not describe. The model reported insufficient evidence for 16 abstentions and unsupported activity for 9; those explanations still need staff review.

Sample composition by permit type

Confidence and processing time

The saved batch took about 125 seconds, with a median request time of 3.53 seconds and a 95th-percentile time of 7.27 seconds. This describes one run's processing time; it excludes staff validation and does not establish future service speed or cost.

These counts apply to assigned categories only. Self-reported confidence is not a probability of correctness, and high confidence in OUT OF SCOPE is confidence in abstention—not a category to fill. Prior confidence analysis pools older labeled results from multiple models; it is not calibration of this expanded Muse Glimmer prompt.

Takeaways

A path to completing the blank fields

  1. Audit all missing values first: identify entirely blank permits, partially labeled permits, conflicting descriptions, missing IDs, and records lacking useful text. The current sampling rule covers only the entirely blank, consistent-description group.
  2. Validate the expanded prompt: have permit staff independently label a fresh sample across all 21 work types and permit families. Measure per-type errors, assignment coverage, and abstention quality before choosing any automatic-fill threshold.
  3. Scale in reviewed batches: classify each eligible permit once, save its proposed type, explanation, model/prompt version, and review status. Route abstentions and uncertain or unsupported proposals to staff. Collect missing details when the description cannot support a label.
  4. Approve and propagate: after review, apply the accepted work type to the permit's associated segment rows. Preserve the original value, staff decision, and change history; do not overwrite existing labels.
  5. Resolve the remaining blanks: handle partial-label conflicts and missing descriptions through reconciliation or follow-up. AI proposals can help complete the dataset, but cannot reliably fill every blank without adequate evidence and review.
This is a proposal-and-review workflow, not a completed update of City records. No work types are written back by this website, and no new model calls are made when visitors open it.
